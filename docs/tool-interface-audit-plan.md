# 工具接口、工作流连接与结果语义审计计划

编制日期：2026-10-20。规划基线：`f57d0f91454ee0c99cf462ac9093bdf68349991a`。
本文是待执行计划；本次仅进行文件盘点、既有报告阅读和方法资料核对，未执行全量工具审计或重跑测试。

## 1. 目标与边界

目标：让每个声明支持的分析路径，都有证据说明实际工具版本、输入、调用、输出、样本归属和下游解释一致；发现不匹配后修复并验证。

主流程：盘点实际调用 → 锁定工具及数据库版本 → 找到官方仓库 → 阅读对应版本说明、CLI 和必要源码 → 建立输入输出契约 → 比对实现 → 最小修复 → 真实节点验证 → 子工作流回归 → 端到端验收 → 记录证据。

范围包括 `modules/`、`subworkflows/`，并沿调用关系覆盖 `main.nf`、`conf/`、`nextflow.config`、`envs/`、`containers/`、`bin/` 与相关测试。科学方法变化另列任务，明确对结果可比性的影响。

所有模块均登记；按风险安排审查深度和顺序。没有差异的实现可以审计通过而不修改。版本升级、替换工具、改变默认算法不能混入普通接口修复。

## 2. 当前起点与证据限制

按当前目录统计：32 个自定义 `.nf`、52 个 nf-core `.nf`、16 个子工作流，以及 `tests/nf-test/` 下 22 个 `.nf.test` 文件。文件数不是工具数、运行节点数或覆盖率分母；阶段 A 需解析 include、别名与可达分支后建立正式清单。

可复用资产：

- `modules.json` 的上游模块 revision；环境与容器声明。
- `tests/nf-test/README.md` 的 P0–P4 分级、数据锁文件及运行入口。
- `tests/nf-test/COVERAGE.md`、`REAL-NODES-RESULTS.md` 与 `results/nf-test/` 的历史证据。
- `docs/fact-reliability-audit.md` 以及现有修复计划中的问题线索。

已观察到的规划依据：

- COVERAGE 与 REAL-NODES-RESULTS 中 Platon、Recycler 等状态不同，必须关联实际运行、代码版本和日志后统一。
- 既有报告明确区分真实、stub、失败与环境阻塞；继续保留这种区分。
- 部分历史通过仅覆盖空结果或执行契约，例如稀疏 HiFi fixture、空质粒统计分支；不能推导阳性路径已覆盖。
- OPERA-MS 的输出选择包含候选路径和搜索回退，优先核验最终结果身份。
- 旧科学审计中的 MAG 路由、丰度与统计、报告产物等问题属于待复核线索，不能未经检查当作当前仍存在的缺陷。

本轮计划未重新证实旧报告中的上游仓库可用性、数据库大小或环境故障；执行时重新核验并记录日期。

## 3. 台账与状态模型

执行阶段建立 `docs/tool-audit/`，原始运行产物放在 `results/tool-audit/<run-id>/`。下列文件为计划产物，目前尚未创建：

| 产物 | 内容 |
| --- | --- |
| `inventory.tsv` | module/process/别名、调用者、平台、启用条件、实际命令、脚本、环境、测试入口 |
| `contracts/<id>.md` | 生物学用途、版本、参数与默认值、输入输出格式、空结果与错误语义、消费者 |
| `findings.tsv` | 问题编号、证据、严重度、影响路径、修复决定、责任人、状态 |
| `runs.jsonl` | 运行与代码/环境/数据标识、命令、退出码、断言、日志、限制 |
| `status.md` | 从台账生成的覆盖与阻塞视图，避免重复手工维护多个状态表 |
| `acceptance.md` | 本轮支持矩阵、已验证范围、未决问题、结果变化与发布结论 |

每条契约至少记录：官方仓库 URL、tag/commit、文档永久链接及定位、获取日期、工具实际版本、镜像 digest 或环境锁、数据库/模型版本和校验和、输入数据校验和、Nextflow/nf-test/Java 版本、执行后端及架构。

分开记录三类状态：

- 审计：`not_started / investigating / matched / mismatch / evidence_missing`。
- 修复：`not_needed / planned / in_progress / ready / merged`。
- 验证：`not_run / pass / fail / blocked`，并注明 `static / stub / real-node / integration / scientific-benchmark`。

`vendored` 仅表示来源，不等于测试通过；空结果通过、分支合法未执行和环境阻塞单独记录。旧运行若缺代码 SHA，标记历史证据，不自动认证当前实现。

## 4. 风险排序与批次

先处理可能静默产生错误结果、混样或丢样的问题，其次处理核心路径不可运行、依赖不可复现，再处理可选工具与文档一致性。严重度使用 S0–S3，避免与既有测试等级 P0–P4 混淆。

| 级别 | 判据 | 处理要求 |
| --- | --- | --- |
| S0 | 样本错配、错取结果、错误单位进入统计等潜在静默错误 | 支持路径放行前解决 |
| S1 | 核心路径失败、关键输出缺失、版本或数据库不可重建 | 核心路径放行前解决 |
| S2 | 可选路径局限、边界输入处理、非核心兼容问题 | 修复或明确排除支持并给出原因 |
| S3 | 不影响执行的注释、文档、来源记录问题 | 随批次整理 |

批次顺序：

1. 校准批次：Platon（已有真实测试）、OPERA-MS（启动与输出）、Recycler（图/BAM/k 值）、PLASMID_DETECTION（可选分支和样本合并）。
2. 核心路径：QC/组装 → 检测/共识/结构 → coverage/abundance → 报告。nf-core 模块重点检查本地配置、覆盖参数和上下游接线。
3. 结果语义：跨样本 feature ID、统一参考、计数单位、DESeq2 输入、分组与空结果、MAG 输出路由、宿主证据解释。
4. 可选能力：typing、annotation、host/linking、comparative、复杂数据库工具；资源受限任务保持独立队列。
5. 平台与发布回归：Illumina、assembly、ONT、hybrid、HiFi 的支持路径和配置组合。

## 5. 阶段 A：盘点与基线重建

输入：基线提交、当前配置、代码与既有测试材料。

动作：

1. 列举 process、workflow、include/alias、启用条件、外部命令和 `bin/` 调用，区分自研算法与第三方工具包装。
2. 建立依赖图：producer → channel/转换 → consumer；识别未使用模块、默认路径、可选分支和不支持组合。
3. 解析实际 profile、`withName`、`ext.args`、容器覆盖与 Conda 声明，区分“声明版本”和“实际执行版本”。
4. 核对历史 JUnit/log/trace 与代码版本；对冲突状态追溯原始证据，不能简单选择较新文档。
5. 选择默认核心路径建立当前运行基线，记录现有失败，不把已有失败归入新补丁。

交付：完整 inventory、支持矩阵、依赖图、历史证据迁移表、首批优先队列。
退出条件：每个 `.nf` 文件均有归属；每个支持路径可定位到模块和测试；未知项明确标记。

## 6. 阶段 B：版本与官方证据

每个第三方命令按下列顺序查证：

1. 从环境包元数据、官方主页、论文的软件链接或 nf-core metadata 确认官方仓库，避免同名项目。
2. 确认实际运行的版本/构建，再找到对应 release/tag/commit。Conda 与容器不一致时分别登记，确定支持组合。
3. 查对应版本的 README、manual、examples、release notes；读取部署环境中的 `--help`、版本命令。
4. 参数含义或输出路径不明确时定位该版本的参数解析器、输出写入代码及上游测试。
5. 文档与运行矛盾时保留双方证据，用最小复现判定实际行为；实现决定运行行为，但仍需判断是否符合分析目的。

每个关键论断记录“上游依据 → 本地位置 → 匹配/差异 → 影响 → 验证方式”。分支首页或最新版 README 只能用来发现资料，不能替代固定版本证据。

数据库、模型、索引单独锁定；镜像 tag 和版本范围不足以保证可重复安装，需记录 digest、锁文件或构建/下载校验信息。native 工具记录路径、版本、构建来源及依赖。

交付：contracts 与 evidence。退出条件：核心参数和输出均有依据；无法确认的项保持 `evidence_missing`。

## 7. 阶段 C：契约比对

| 层次 | 必查项 |
| --- | --- |
| 生物学用途 | 支持的测序平台、输入类型、算法模式、阈值含义、数据库适用性 |
| 命令 | 可执行入口、子命令、必填参数、互斥选项、默认值、CPU/内存与资源声明 |
| 输入 | FASTA/FASTQ/GFA/FASTG/BAM 类型、压缩、配对、排序、索引、contig ID、图与比对的共同来源 |
| 执行环境 | 容器/Conda/native 一致性、依赖、模型路径、线程、架构、随机种子（若支持） |
| 输出 | 最终产物身份、命名、数量、格式、表头、单位、ID、版本差异、空结果 |
| Nextflow | tuple 结构、meta 键、channel 类型、join/mix/group、广播、重复键、缺失样本、optional output |
| 下游解释 | 列名/位置解析、分数方向、计数与丰度、缺失与零值、ID 映射、统计假设 |
| 发布与恢复 | publish 产物完整性、旧结果隔离、显式数据依赖、失败传播、resume 缓存边界 |

子工作流必须检查：多个样本乱序到达、可选工具关闭、工具开启但某样本无结果、重复 ID、缺失结果、所有结果为空。join 的具体策略按项目实际 Nextflow 版本验证；可选缺失与意外丢样需分别定义，不能统一静默忽略。

自研脚本没有外部工具仓库时，以本项目明确的方法定义、输入输出契约和独立参考计算审查，不能给它们虚构上游依据。

交付：分级 findings 与最小修复方案。退出条件：每项差异都有受影响路径和可判定的验收断言。

## 8. 阶段 D：修复规则

- 每个补丁围绕一个工具或不可拆分的接口变更；更新生产者与消费者时作为同一完整修复。
- 优先修本地参数、环境或适配逻辑。修改 vendored 模块时保留上游 SHA 与本地差异说明，避免以后更新覆盖修复。
- 输出路径必须对应文档或源码定义的最终结果；不得靠“任意找到一个文件”掩盖输出契约失配。
- 空生物学结果、禁用分支、上游错误三者分别处理；禁止把执行错误改为空结果成功。
- 不硬编码只适合 fixture 的 k 值、路径或样本名；参数来源应与实际上游产物一致。
- 生物学阈值、统计模型或工具版本改变时记录结果兼容性，单独评估历史结果是否需重算。
- 对环境无法重建的工具，记录具体阻塞、恢复路径和支持状态；不能仅凭一次 404 判定永久不可用。

交付：最小补丁、证据和回归测试。退出条件：相关真实测试通过；未解决部分明确标记。

## 9. 阶段 E：验证矩阵

沿用仓库 P0–P4 命名；科学性能验证单独记录，不与执行等级混算。

| 验证范围 | 目的 | 验收 |
| --- | --- | --- |
| 静态/配置 | 语法、参数展开、版本和路径声明 | 解析正确；不能据此声称工具可运行 |
| P0 | 非法输入、不支持组合、缺依赖 | 在规定位置明确失败；无不应运行的分析任务 |
| P1 | vendored 模块 | 固定 revision 的相关上游用例；真实与 stub 分开 |
| P3 | 修改模块的真实节点 | 退出码、文件格式、关键记录/单位、ID 与空结果语义 |
| P2 | 平台与子工作流 | 样本无丢失/重复/错配，分支状态及下游结果符合契约 |
| P4 | 多样本链路 | 非空与空结果均覆盖；统计、网络及报告分支实际执行状态可见 |
| 科学基准 | 检出、分箱、关联或统计的效果 | 独立参考真值与预先定义的指标；不使用首次输出反推“真值” |

每个相关修复优先覆盖真实阳性、真实阴性/无检出与必要边界场景。纯路由/格式测试可以用明确标记的小型人工 fixture，但不计入真实工具或科学性能通过率。遵循既有真实测试套件的数据要求。

断言优先验证语义：FASTA ID/长度与来源、BAM reference 与排序、TSV 表头/类型/单位、样本计数与归属。非确定性输出使用有依据的容差或集合比较；不得为通过测试删除关键断言或直接更新快照。

现有 ENA 测试若质粒表为空，只证明该空结果路径；还需独立非空输入验证 DESeq2/网络等开启分支。小数据库或裁剪数据只能支持其实际覆盖的结论。

执行顺序：相关单元/解析测试 → 真实 P3 → 受影响 P2 → 必要 P4 → 发布支持矩阵。固定数据、环境与参数后，同一输入直接 CLI 运行和 `.nf` 包装结果的比较可用于定位包装差异，但不能替代独立生物学真值。

每次保存 run-id、代码 SHA/未提交补丁摘要、数据与数据库校验、环境标识、完整命令、退出码、JUnit、trace、`.command.sh`/stderr 与关键输出。新验证使用隔离输出目录；缓存命中单独标记，版本/模型改变时验证缓存有效性。

## 10. GitHub 与 Codex 工作单

GitHub 用于固定来源、关联问题与补丁、保存审查和 CI 证据；Codex 按可验收的小任务执行。当前任务仅产出计划，尚未创建远程 issue/PR、推送或发布。

每个工作单采用以下模板：

```text
任务 ID / 标题：
目标行为与生物学用途：
基线提交、范围、依赖任务：
涉及的模块 / 配置 / 脚本 / 下游：
工具、镜像、数据库、模型版本：
官方证据永久链接与定位：
当前行为 → 预期行为：
风险与最小修改方案：
验证数据、运行命令、独立预期与断言：
资源预算（CPU、RAM、磁盘、下载量、时限）：
完成标准：
实际结果与产物路径：
未决项、限制、回退方式：
```

研究、实现、验证与复核为不同检查步骤，可由同一执行者顺序完成；计划不依赖多代理并发。审查必须重新检查原始证据与实际 diff，而非仅接受实现摘要。

PR 单元建议为一个工具契约或紧耦合子工作流；描述列出问题、前后行为、固定版本依据、实际验证、未执行项与结果兼容性。修改配置/版本后跑直接依赖及必要消费者回归。

未来 CI 分层：普通变更跑廉价静态与相关测试；具备依赖的运行器跑真实节点；定期或发布前跑平台及大型数据库测试。缓存键包含工具/数据库/测试数据标识。缺数据库显示 blocked；stub 不替代真实验证。保留日志与支持矩阵。

## 12. 完成标准与后续维护

全量审计完成标准：

- inventory 中所有对象均有结论：匹配、已修复、证据不足、环境阻塞或不支持；待审对象为零。
- 声明支持路径中 S0/S1 未决为零；通过项有对应代码/环境/数据版本与真实验证。
- 每个子工作流的关键样本关联、可选分支和空结果规则得到验证。
- 工具/数据库/模型和自研解析语义可追溯；文档、支持矩阵与证据一致。
- 保留科学准确性尚未验证的限制，不将执行通过宣传为性能保证。

“审计完成”与“全部能力可发布”分别报告。某项可完成审计但运行仍 blocked；其不得计为验证通过。若排除出支持范围，必须同步入口提示与文档，不能靠改分母制造全绿。

指标分别报告：已审计/全部对象、真实节点已验证/声明支持节点、平台路径已验证/声明支持路径、非空分支覆盖、未决 S0/S1 数、可复现环境覆盖。每项同时给出分母、失败和阻塞数量。

回退保留上一可验证提交及工具/数据库锁，使用新输出目录重跑；结果格式变化要保留迁移说明。以后新增工具、升级版本/数据库、改变 CLI 参数、修改解析器或 channel 接线时，更新契约并重跑受影响验证。

## 13. 方法依据

以下资料用于制定方法，具体工具调用仍需对应版本的独立取证：

- [nf-core/modules](https://github.com/nf-core/modules/blob/master/README.md)：模块复用与上游 commit 追踪；本项目已有 `modules.json` 可复用。
- [nf-core 组件审查清单](https://nf-co.re/docs/contributing/reviewing-pull-requests/review_checklists/component)：模块输入输出、元数据和测试审查。
- [Nextflow operators](https://docs.seqera.io/nextflow/reference/operator)：channel 操作与 join 行为；执行时使用项目固定运行时对应文档。
- [OpenAI：Iterating Development Workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)：明确任务上下文、阶段产物、持续进度记录与验证。本文工作单和证据台账是针对本仓库的设计。
